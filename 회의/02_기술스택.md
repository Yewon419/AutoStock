## 논의 포인트별 옵션

### 1. Backend

| 옵션 | 장점 | 단점 |
|------|------|------|
| **FastAPI** (기존 유지) | Python 생태계, pykrx 연동 편함, async 지원, 기존 경험 | - |
| Django | 풀스택 기능 많음 | 자동매매엔 과함 |

→ **FastAPI 유지 유력** (pykrx, 자동매매 비동기 처리에 잘 맞음)

---

### 2. Frontend

| 옵션 | 장점 | 단점 |
|------|------|------|
| **Vanilla JS** (기존) | 빠름, 의존성 없음 | 복잡한 대시보드 관리 힘듦 |
| **React** | 컴포넌트 관리, 생태계 풍부 | 러닝커브, 빌드 필요 |
| **Vue 3** | 가볍고 직관적, 배우기 쉬움 | React보다 생태계 작음 |
| **Svelte** | 번들 크기 작음, 빠름 | 생태계 작음 |

→ 자동매매 대시보드 특성상 실시간 업데이트, 다중 전략 뷰 등 복잡도 있어서 **프레임워크 검토 필요**

---

### 3. Database

| 옵션 | 장점 | 단점 |
|------|------|------|
| **PostgreSQL + TimescaleDB** | 시계열 최적화, DB 하나로 통합 | 설정 필요 |
| PostgreSQL + InfluxDB (기존) | 역할 분리 | DB 두 개 관리 복잡 |
| PostgreSQL 단독 | 단순함 | 시계열 쿼리 느릴 수 있음 |

→ **TimescaleDB로 통합** 유력 (주가 데이터 = 시계열, InfluxDB 없애서 단순화)

---

### 4. 스케줄러 / 작업 큐

| 옵션 | 장점 | 단점 |
|------|------|------|
| **Airflow** (기존) | 강력한 DAG 관리, 모니터링 UI | 개인용엔 무거움, 설정 복잡 |
| **Celery + Redis** | 가볍고 충분함, 비동기 처리 | DAG 개념 없음 |
| **APScheduler** | 초경량, 코드 내 통합 | 분산 처리 불가 |

→ 자동매매 여러 전략 동시 운영 특성상 **Celery + Redis** 유력 (Airflow는 오버스펙)

---

### 5. 인프라

| 옵션 | 장점 | 단점 |
|------|------|------|
| **Docker Compose** (기존 유지) | 개인/가족용에 충분, 관리 쉬움 | 스케일아웃 불가 (필요 없음) |
| K8s | 확장성 | 개인용엔 완전 오버스펙 |

→ **Docker Compose 유지**

---
